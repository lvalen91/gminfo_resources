# Pi-swap feasibility (replacing the A11 radio with a Raspberry Pi running AAOS)

Scope: whether a Raspberry Pi 4/5 (or CM4/CM5) running custom AAOS could replace the OEM A11 radio while reusing the existing vehicle wiring: CAN audit of the head unit, wake/status path, radio-removal consequences, audio and panel/touch interconnects, capture plan, recommendations.
Evidence base is the Y181B clean-room firmware, owner real-vehicle tests, and GM service data. All Pi-side statements are inferred; no Pi hardware has been tested.

Evidence tags (this doc):
- CAN audit and capture plan: **[FW]** confirmed in firmware, **[INF]** inferred from firmware structure, **[VEH]** confirmed by the owner's real-vehicle test, **[GM]** general GM-platform knowledge, **[C]** confirmed (live capture), **[X]** external (other vehicle).
- Audio/panel sections: **[confirmed-fw]**, **[confirmed-vehicle]**, **[confirmed-service]** (GM ALLDATA / prior repo docs), **[inferred]**, **[general]**.

Related: [vehicle_network.md](vehicle_network.md) (topology, bus map, vlan tables), [can_network.md](can_network.md), [vip_ipc_ghs.md](vip_ipc_ghs.md), [avb_audio_transport.md](avb_audio_transport.md), [vehicle_config.md](vehicle_config.md), [ethernet_networking.md](ethernet_networking.md), [hardware_specs.md](hardware_specs.md), [fsa_protocol.md](fsa_protocol.md), [ota_programming_roles.md](ota_programming_roles.md), [../hardware/connectors.md](../hardware/connectors.md).

## Summary of conclusions

- A Pi does not need to speak CAN. The radio presents to the vehicle as an automotive-Ethernet node (FSA/SOME-IP on vlan4/vlan5, AVB audio) and as CAN ECU 0x80 only across the GHS/VIP IPC boundary inside the radio's own SoC, which a Pi cannot reproduce. [INF]
- The integration problems are Ethernet/FSA, AVB audio (including all chimes) and the GHS-hosted camera compositing, not CAN.
- Audio: first cut should be the analog/USB-DAC fallback; real AVB only after a bench capture of the A11-T3 stream.
- Panel: commodity touchscreen driven natively by the Pi, unless dash fit is mandatory; OEM panel needs bespoke FPD-Link III bridge hardware.

## 1. CAN feasibility audit (firmware-grounded, 2026-09-27; updated 2026-11-17)

Image: `.../update_packages/Y181B/mountables/Y181B_cleanroom.img`, build `W231E-Y181.3.2-SIHM22B-499.3`, Android 12, kernel **4.19.305**, x86_64 Intel Gen8 CSM, read via `7z` (no ext4 mount on this host).

### 1.1 The Android/AAOS guest has no CAN interface

- **No CAN driver anywhere.** Zero `can`/`socketcan`/`vcan`/`flexcan`/`slcan`/`j1939` kernel modules in either module set: the generic `os/vendor/lib/modules/` blob (**324 `.ko`**, an upstream x86 collection: `bcmdhd`, `ath3k`, `dell-smm-hwmon`, etc., not all loaded) and the actually-loaded first-stage set in `boot/ramdisk_root/vendor/lib/modules/` (**11 modules**: `igb_avb, dwc3[-pci], xhci-{hcd,pci}, ti949_serdes, faceplate, atmel_mxt_ts, mei[-me], dynamic_spi_node`). [FW]
- **No CAN netdev is ever brought up.** No `ip link ... type can`, `slcan`, `ifup can*`, or `/dev/can*` in any `.rc` or shell script in system/vendor. [FW]
- **No CAN symbols in the vehicle stack.** `strings` on `gmvt`, `gmvt_client`, `android.hardware.automotive.vehicle@2.0-service-gm` (the GM VHAL), `IPCServer`, `vehicleaudiocontrol` shows no `socketcan`/`AF_CAN`/`gmlan`/`can0`/arbitration-ID handling. [FW]
- **Kernel `CONFIG_CAN` is settled.** Live `/proc/config.gz` is captured in every gm_enum run (Y175 and Y181): `CONFIG_CAN=y`, `CONFIG_CAN_RAW=y`, `CONFIG_CAN_BCM=y`, `CONFIG_CAN_GW=y`, `CONFIG_CAN_SLCAN=y`, `CONFIG_CAN_DEV=y`; `CONFIG_CAN_VCAN`/`CONFIG_CAN_VXCAN` explicitly unset. The CAN subsystem is built in but inert: no transceiver driver, no netdev bringup, no consumer, matching the modules/netdev/strings evidence. **[C GM_research .../analysis/adb/Y175/gm_enum_20260117_081801/raw/kernel_config.txt:1376 (+ Y181 gm_enum captures); FW for the modules/netdev/strings.]** History: an earlier "IKCFG inside the compressed bzImage would not decompress" note was a firmware-side limitation; the live config.gz settles it.
- **`gmvt` caveat.** `gmvt` (runs as `audioserver`, cap `NET_RAW`) is **GM Voice** (VA/VR; see `/vendor/etc/gmvt.cfg`: PCM nodes, VTC voice-tuning configs), not "GM Vehicle Transport." Its `NET_RAW` is for a voice stream socket, not vehicle CAN. Do not cite it as a vehicle-network daemon. [FW]

### 1.2 How the guest reaches the vehicle

Two paths, both confirmed from the guest side. Full IPC/GHS architecture lives in [vip_ipc_ghs.md](vip_ipc_ghs.md); topology in [vehicle_network.md](vehicle_network.md).

1. **GHS hypervisor IPC mux.** The box runs Android as a Green Hills INTEGRITY guest (`/vendor/bin/ghs_set_is_virt.sh`: `is_virt=true` iff `/dev/ghs` exists). `IPCServer` ("**GhsComms**", `GhsCommsRx/TxThread`) multiplexes numbered logical channels over a UART-backed link and exposes them as `/dev/ipc/ipcN` sockets. Config `/vendor/etc/ipc4.cfg`: `com_device=/dev/ttyS1`, `com_speed=1000000`, `protocol_version=0x10`, `socket_prefix=/dev/ipc/ipc`, control iface `/dev/ipc/ctrlif_s` (gid `vehicle_network`), **lchannels index 0-20**. The GM VHAL opens **`/dev/ipc/ipc3`** = lchannel index 3, gid `vehicle_network`, the vehicle-signal channel. (`IPCServer` strings also reference `/dev/ghs/ipc` and `/dev/ttyS4`; the authoritative backing device per config is `/dev/ttyS1`.) [FW]
   - Confirms and refines the vehicle_network Join-points note ("VIP-SoC HDLC IPC `/dev/ttyS1`, 20 channels 1-20 ... Android never sees raw CAN"): same UART, same channel count. The peer at the far end of `/dev/ttyS1` (VIP MCU / a GHS partition) owns the physical CAN; the guest sees only cooked signals over IPC channel 3. [FW for the guest half; the far-end "VIP MCU" identity is prior project analysis, [INF]/[GM] for this build.]
   - **Power sequencing, updated 2026-11-17:** VIP firmware and bench CAN tests now establish power/lifecycle processing independently of AAOS. The driver-door/off sequence can initiate SoC shutdown; a mute-hold CAN sequence can request reset. This supersedes the earlier owner-only inference. It does not replace a physical measurement of individual supply rails. See [can_network.md](can_network.md) and the VIP lifecycle evidence in `../hardware/teardown.md`.

   **Native Probe08 follow-up (2026-11-17).** With stock AAOS/GHS absent, `/dev/ttyS1` on PCI `00:18.1` exchanged CRC-valid HDLC traffic with VIP at 1 Mbps. The bounded tool received a protocol-`0x10` channel-0 flow-control message (21 entries), then six channel-3 messages, with zero bad CRCs. The short channel-3 payloads were `E1 02 10 00 01`, `E1 03 10 00 01`, `E1 01 10 00 01`, followed by the same three variants ending in `02`. Their application semantics remain unresolved; repetition may indicate negotiation/retry, but they are not yet decoded vehicle-property values.

   During that test, changing the bench's CAN `284` candidate from value 2 to 4 and back to 2 produced VIP diagnostic state changes to `Propulsion` then `Run`; the original value was restored. No corresponding new vehicle signal payload was decoded by the native receiver. This confirms that VIP continues CAN power-state processing without AAOS, while the SoC application handshake/subscription requirements remain unresolved. The already-confirmed CAN `4DA` driver-door path is documented in [can_network.md](can_network.md); engine RPM and turn-signal UART forwarding were not newly tested here. The link exposes binary IPC, not a VIP shell, and does not establish unrestricted CAN injection, raw bus capture, or unrestricted memory access.

2. **Automotive Ethernet.** `igb_avb.ko` (Intel IGB + AVB/TSN) on **`eth0`**, brought up by `/system/bin/init_ethernet.sh`: `vlan5` = `192.168.1.100/24`, `vlan4` = `172.16.4.100/24` ("legacy_network"), static routes/neighbors to the peer ECUs. `daemon_cl` runs gPTP/802.1AS (invoked with `-GM`, `audio` group) and TSN Tspec, i.e. AVB audio + FSA/SOME-IP, the plane-2 topology in [vehicle_network.md](vehicle_network.md). Switch is Marvell (`vendor.harman.ethernetswitch=mrvl`). [FW] Note: the `-GM` flag is a command-line fact; whether the radio is the elected grandmaster is an open conflict (see Open conflicts).

### 1.3 Answer to Q1

For a Pi replacement, **you do not need to make the Pi speak CAN.** The OEM radio node presents to the rest of the vehicle as (a) an automotive-Ethernet node (FSA/SOME-IP on vlan4/vlan5, AVB audio) and (b) a CAN ECU (`0x80`) only via the far side of the GHS/VIP IPC boundary, which lives inside the OEM radio's own SoC and is not reproducible on a Pi. The realistic Pi integration surface is the Ethernet/FSA plane (largely reverse-engineered in [vehicle_network.md](vehicle_network.md) and [fsa_protocol.md](fsa_protocol.md)), not CAN. [INF from FW + existing doc]

## 2. Wake-up and vehicle-status signalling (guest view)

- Power/ignition state arrives as a HIDL service, not CAN NM frames: `vendor.gm.powermode@1.0` (`IPowerModing`, `IPowerModeListener`, `ISystemStateListener`). The VHAL registers for power-mode updates ("Failed to register for power mode updates from Power Moding service"), logs "Current system state: %s power mode: %s", and runs an acknowledge handshake (`acknowledgePowerModeChanged`, "power mode change complete acknowledged"). It carries an explicit `BPMM_START_STOP_IGNITION_SWITCH_PRESSED_REPORT` and an `IGNITION` state. [FW]
- The network-management/wake decision is made on the far (GHS/VIP) side and delivered to Android as discrete power-mode transitions over IPC channel 3; the guest neither sees nor generates CAN NM traffic. [FW for the guest interface; INF that NM lives on the far side.]
- The on-wire GM power-mode frame is an **[X] Cadillac capture** (`0x370`, `bit37:3` = Off/Acc/Run/Crank/Propulsion), not confirmed on this Silverado, and consumed on the CAN/VIP side, not by the guest. It is catalogued in the published-candidate comparison in [can_network.md](can_network.md) (that doc records `0x370` as absent on this radio and the enum as Off=1, Accessory=2, Run=3, Crank=4, Propulsion=5, not to be merged with Global A `0x1F1`). History: the source cited "Plane 1a above" (the SecOC section), which contains no `0x370` content; reference corrected 2026-11 during reorg.
- Vehicle-status signals (speed, gear, doors, accessory) reach apps through the standard AAOS VHAL property model, sourced over `/dev/ipc/ipc3`; the raw-to-property mapping is the bus-frame decode already in progress (Y181 emulator VHAL write path = bus-frame injection via `/dev/ipc/ipc3`; see [emulator.md](emulator.md)). [FW/INF]

## 3. Risk of physically removing the OEM radio node (summary)

Full behaviour is owned by [vehicle_config.md](vehicle_config.md) (removal-risk). Summary of what drives the Pi design:

- **[VEH] measured** with the radio module removed: no rear/360 camera (compositing runs on the GHS partition of the radio's SoC; EVS HALs `android.hardware.automotive.evs@1.0/1.1` are present in the guest); no vehicle audio at all, including turn-signal ticks, door chimes and safety dings (radio is the whole-vehicle audio hub feeding the Bose T3 amp over the bus 6 `A11<->T3` AVB pair, `.103 = AMP_ETH`; `vehicleaudiocontrol` registers a "chime-playback-status" callback gated on `vendor.gm.powermode ISystemStateListener`; `libgmaudiopowermode.so` exists); cluster gauges and safety info unaffected (cluster `.106` Visteon IPC runs its own RTOS; only radio-fed cluster cards go blank).
- **[INF]/[GM] expected, not observed:** "lost communication with radio / IVI" U-code DTCs from modules expecting CAN ECU `0x80` (via gateway `0x45`) and Ethernet node `.100`; SOME/IP-SD peers lose `172.16.4.100`; driver-visible warning vs silent DTC untested. Telematics/OnStar (CGM `.107/.112`, EOCM `.12/.13/.15`) should survive since they depend on the Ethernet fabric, minus any HMI rendered through the radio.
- **SecOC** is a replacement risk, not a removal risk: critical-control frames use OEM-held keys and there is no aftermarket provisioning path (SecOC section in [vehicle_network.md](vehicle_network.md)). A Pi cannot forge SecOC'd frames; irrelevant if it stays on the Ethernet/FSA plane, the recommended posture. [X to INF]
- **Pi-design consequence:** a Pi must source ALL vehicle audio (chimes, turn-signal, seatbelt, safety dings), not just media, and drive the Bose amp over AVB/TSN. Bottom line: safety-critical function (cluster RTOS) is independent of the radio; the radio is the camera compositor and the whole-vehicle audio hub, both on transports (GHS, AVB Ethernet) a Pi does not natively reproduce. CAN is not the integration problem; Ethernet/FSA + AVB audio + GHS-hosted camera are.

## 4. Prioritised bench / in-vehicle capture plan (future hardware-enabled session)

Nothing below is complete except where noted. Redact VIN and any real MACs/IPs before sharing captures (synthetic vs real MACs are already flagged in [vehicle_network.md](vehicle_network.md)).

**Status, updated 2026-11-11 (Y175_2026-11-02 Bus 2 tap bench finding):** item 1's Ethernet Bus 2/4 (gateway/telematics) capture has been executed on the bench via a direct T1 tap (BUELEC 100/1000Base-T1-TX-L media converter, Marvell 88Q2112 + Realtek RTL8211FI, run at 100M, direct to a USB-GbE NIC with no intervening switch; a switch in the path was found to silently strip 802.1Q tags, which was the actual blocker, not duplex). It confirmed the VLAN 2 (AVB) / VLAN 5 (service) / VLAN 4 (internal) tag structure on that pair and the exhaustive port/allowlist map (see Open items #1 and #7 in [vehicle_network.md](vehicle_network.md)). The bus 6 (amp/AVB) tap, the ignition-transition power-mode capture, and the IPC `/dev/ipc/ipc3` decode in item 2 remain not done.

1. **P0, Ethernet is the real interface: capture it first.** Tap the radio's 100BASE-T1 pairs (bus 6 `A11<->T3` amp, bus 2/4 gateway/telematics per Open-items #1) with a BroadR-Reach/100BASE-T1 media converter into a mirror port; `pcap` on `eth0`/vlan4/vlan5 during power-on, ignition on->acc->run->crank, and ignition-off. Goals: (a) observe the FSA `0x5AA5` power-mode/system-state exchange the `vendor.gm.powermode` service consumes; (b) map which SOME/IP-SD services vanish when the radio is pulled; (c) confirm/deny a VLAN-502 CAN mirror on this unit (Open-items #6). Bus 2/4 tagging and the port/allowlist map are DONE (bench, no gateway peer present); the power-mode/ignition-transition capture and bus 6 tap remain open.
2. **P0, decode the IPC vehicle channel.** With the radio powered on a bench harness, log `/dev/ipc/ipc3` (lchannel 3) and correlate against known transitions (ignition, gear, speed) to finish the raw-frame-to-VHAL-property map (ties into the emulator VHAL work). This is the payload a Pi's VHAL backend would ultimately need to emulate. Not done.
3. **P1, power/wake sequencing.** Scope the radio connector's switched-battery / wake / accessory pins during KL30/KL15 transitions to learn what powers the module and whether wake is a hard line or a bus event. Cross-check against `BPMM_..._IGNITION_SWITCH_PRESSED_REPORT` timing.
4. **P1, CAN only if/when needed.** Only if the Pi must originate CAN (it likely must not): tap vehicle CAN at the gateway `0x45` side with a USB-CAN adapter and log NM/wake + status frames during the same transitions. Expect the radio itself not to be a raw-CAN source (per section 1), so this characterises gateway/VIP behaviour, not the radio.
5. **P2, removal-DTC survey.** With a GM-capable scan tool (MDI2/DPS, see `../diagnostics/`), pull DTCs from gateway `0x45` and neighbouring modules before and after radio removal to enumerate which U-codes fire and whether any surface to the driver. Answers the real feasibility-blocker for the swap.
6. **P2, audio-hub scope proof.** Confirm the amp (T3) is a pure AVB-Ethernet sink with no local chime generator, i.e. that a Pi must synthesise every chime/ding and stream it over AVB. (Coordinate with [avb_audio_transport.md](avb_audio_transport.md).)

See also [../hardware/connectors.md](../hardware/connectors.md) (physical harness carrying these buses) and [ota_programming_roles.md](ota_programming_roles.md) (module programming over this network).

## 5. Audio: transport and Pi feasibility

Wire layout, streams, usage-to-bus mapping and replacement-endpoint gaps are owned by [avb_audio_transport.md](avb_audio_transport.md); the 2026-11-15 measured AAF PCM packing, VLAN/priority and public usage map are in the VLAN 2 reference there. Firmware/vehicle facts the Pi reasoning rests on (evidence kept here so the argument is self-contained):

**Two amp paths exist in firmware; this vehicle uses the Ethernet-AVB one.**

- [confirmed-fw] On-SoC audio is Intel SST DSP -> I2S/TDM -> **NXP TDF8532** 4-ch class-D amplifier-codec. Driver `snd-soc-tdf8532.ko` (`sound/soc/codecs/tdf8532.c`, `alias=i2c:tdf8532`) + Intel machine driver `snd-soc-sst_bxt_tdf8532.ko`. Amp control is I2C: `init.audio.rc` chowns `/dev/i2c-3` to `audioserver` (matches [hardware_specs.md](hardware_specs.md): "i2c-3 = TDF8532 codec control").
- [confirmed-fw] A full automotive Ethernet AVB audio stack gates audio bring-up:
  - `vendor/lib/modules/igb_avb.ko`: Intel I210 GbE driver with AVB/TSN extensions (mainline `igb` disabled per hardware_specs.md).
  - AVB StreamHandler service (COVESA/GENIVI-style, IEEE 1722/AVTP). `init.audio.rc` blocks on `init.svc.vendor.avbstreamhandler=running` and `vendor.avb.streamhandler.ready=true` before starting PulseAudio and the audio HAL.
  - `service vendor.earlyavbaudio /vendor/bin/early_audio_alsa_avb.sh`: early-boot AVB audio, before Android is fully up; likely carrier for safety-relevant early chimes.
  - Route/param configs select transport: default `persist.vendor.audio.audioConf = AudioParameterFramework-tdf8532-no-eavb.xml` (local I2S to TDF8532), alternates `...-eavb-master-raw.xml`, `...-eavb-master.xml`, `...-eavb-slave.xml`, keyed on `persist.vendor.eavb.mode` and AVB profile names `MRB_Master_Audio` / `MRB_Slave_Audio` (IEEE 1722a compatibility flag `d6_1722a`). Same SST DSP, switchable output route.
- [confirmed-service] For this vehicle the active path is Ethernet AVB to an **external Bose T3 amplifier**: GM ALLDATA Data Link Communications data records physical Ethernet **bus 6 (ports 7214/7215) = A11<->T3 Bose amp, "the AVB audio pair."** The source states the A11's Intel I210 is gPTP grandmaster for that AVB domain (hardware_specs.md); this conflicts with the 2026-11-15 correction that packet presence does not establish elected role (see Open conflicts). The default `no-eavb` config in the generic image is a base-trim/build fallback; the LTZ-with-Bose truck streams IEEE-1722 audio over Ethernet to T3. The local TDF8532 I2S path is almost certainly the base-audio, no-Bose variant [inferred].
- [confirmed-vehicle] **Scope increase: the radio is the whole vehicle's audio hub.** With the A11 removed the owner had no audio at all, no media, no turn-signal ticks or door chimes. Chimes/turn-signal audio are generated by a body/chime module elsewhere but rendered to the speakers through the radio. Consistent with both firmware facts: the radio is either the mixer/source of that audio or the AVB gPTP grandmaster; remove it and the AVB clock domain collapses and T3 goes silent regardless of who sourced the stream. A Pi cannot just "play infotainment audio"; to preserve today's behaviour it must also (i) act as gPTP grandmaster for bus 6 (if the radio is indeed the grandmaster; unresolved), and (ii) carry/relay the chime/turn-signal audio path to the speakers. Dropping (ii) means losing turn-signal and seatbelt/door chime audio, an FMVSS/NHTSA-adjacent expectation (e.g. seatbelt-reminder audibility); a real safety/legal tradeoff, not a nicety.

**Audio feasibility (Pi):**

- **AVB reuse is plausible and is the same physical network already decoded (FSA), just a different pair/protocol. [inferred, medium confidence]** Linux has the pieces: a TSN-capable NIC (Intel I210/I225/I226, or a USB/HAT with TSN), `linuxptp` for 802.1AS/gPTP (the Pi would need to be grandmaster), kernel `AF_PACKET`/ETF/TAS qdiscs + `libavtp`, and the open-source COVESA AVB StreamHandler, the component this firmware runs. The Pi 4/5 on-board NIC is not TSN/AVB-capable, so this needs an add-on TSN NIC; a CM4/CM5 + carrier with an I210/I226 over PCIe is the realistic route. Hard parts: matching Bose T3's exact AVTP stream format, admission/control, and gPTP timing. **Updated 2026-11-15:** active AAF PCM packing, VLAN/priority and public usage map are measured in the VLAN 2 reference ([avb_audio_transport.md](avb_audio_transport.md)); Bose admission, presentation timing and control remain unresolved. SRP requirements are unverified.
- **The local-I2S TDF8532 path is not a realistic Pi target. [inferred]** It presumes a directly wired NXP amp with proprietary I2C control; a Pi's I2S/TDM to a foreign amp is fragile and this truck's amp is external over AVB anyway.
- **Pragmatic fallback [general]:** do not preserve the OEM amp bus. Feed the existing speakers from a Pi audio out (analog line-out via USB/HAT DAC, or the Pi driving a simple aftermarket class-D amp), accepting loss of Bose DSP tuning and, critically, arranging chime/turn-signal audio some other way (or accepting its loss, with the safety caveat above).

## 6. Panel and touch

Platform note: Intel Apollo Lake / "broxton", x86_64, kernel 4.19.305, Android 12 under the GHS hypervisor, not ARM/Qualcomm. Audio and display blocks are Intel-SoC peripherals (Intel SST/SOF DSP, i915 display), so a Pi (ARM, VideoCore/DSI) is a different silicon family at both ends. Firmware evidence: `Y181B_cleanroom.img` (ext4, read via `7z`; not mountable on macOS, no `debugfs`).

- [confirmed-service] Panel is **Chimei Innolux DD134IA-01B, 2400x960 @ 60 Hz, ~13.4"** ([hardware_specs.md](hardware_specs.md); system `lcd_density=200`, physical ~193 dpi).
- [confirmed-fw] The display link is **TI FPD-Link III, not raw LVDS from the SoC.** Driver `ti949_serdes.ko` (`drivers/video/gm-serdes/ti-949.c`) is a TI **DS90UB949** serializer; its recovery routine `reinit_ti949_948` names the partner **DS90UB948** deserializer at the panel. Signal chain (corrected 2026-11-17 from TI device documentation): i915 HDMI -> DS90UB949 serializer -> single FPD-Link III coax/STQ -> DS90UB948 deserializer at the panel -> LVDS into the panel TCON. "LVDS" is the last hop only, downstream of the deserializer. Serializer control is I2C: `init.bxtp_gm.rc` chmods `/dev/i2c-7` and `insmod`s `ti949_serdes.ko`; a `949-errata-fix` service and `evs_app` run alongside (serdes init lives in the EVS/camera mixin).
- [confirmed-fw] Touch = **Atmel maXTouch** (`atmel_mxt_ts.ko`, `insmod` at `init.bxtp_gm.rc:73`), on **I2C bus 7 at 0x4B** (`.../atmel_mxt_ts/7-004b/reinit_mxt`; matches hardware_specs.md "Atmel maXTouch, I2C-7 @ 0x4B"). The "16-point multitouch" figure is from the Y177 snapshot only; hardware_specs.md marks it UNVERIFIED on Y181 (no `getevent -p` capture), qualified 2026-11-12.
- [inferred, high confidence] **Touch I2C is tunneled back over FPD-Link III.** The maXTouch and DS90UB949 share the same i2c-7 bus, and `reinit_mxt` is paired with `reinit_ti949_948` (re-init serdes, then re-init touch after a link drop). In FPD-Link III the DS90UB948 bridges a remote I2C segment back over the coax to appear as a local bus on the head unit. The display is an integrated module (LVDS panel + DS90UB948 + Atmel maXTouch) joined to the radio by one FPD-Link III coax carrying forward video + a bidirectional back-channel I2C (touch + serdes + backlight control).
- [confirmed-vehicle] With the radio removed there is no rear/360-camera overlay on the display: camera compositing (EVS: `evs_app`, `earlyEvs_harman`, the 949 errata service) runs on the radio's own Intel SoC/GHS. This independently confirms the panel is driven directly by the radio's SoC, with no separate video ECU in the path. (Owner also confirms the instrument cluster is a separate independent RTOS, unaffected; out of scope.)

**Panel/touch feasibility (Pi):**

- **Video: a bridge-chip problem, not raw LVDS. [inferred/general]** A Pi has no LVDS or FPD-Link III output. To drive this OEM panel the Pi must originate FPD-Link III, i.e. drive the panel's DS90UB948 from a Pi source. Practical route: Pi HDMI -> a compatible DS90UB949 serializer -> the panel's 948; or replace the panel-side deserializer board. Serializer input interfaces are not interchangeable. Buildable from catalog TI FPD-Link III parts but bespoke integration (link training, I2C-passthrough mapping, backlight/PWM, exact DS90UB948 strap config), not plug-in. Panel timing for the 2400x960 mode must be matched (not fully enumerated in firmware; **open**).
- **Touch: the tractable half. [inferred, high confidence]** If video is otherwise solved, the maXTouch is a standard I2C device (0x4B) with a mainline `atmel_mxt_ts` driver; a Pi can read it directly on one of its I2C buses (plus the maXTouch CHG/interrupt line), independent of the FPD-Link back-channel, if the controller can be wired to the Pi's I2C rather than trapped behind the deserializer. If it must stay behind the 948, the Pi gets it via the serializer's I2C passthrough, the same bridge work as video.

## 7. Recommendation

- **Audio:** the OEM path is worth considering because it rides the already-mapped automotive Ethernet: a CM4/CM5 + TSN NIC running linuxptp + the open COVESA AVB StreamHandler could in principle re-originate the bus-6 AVB stream to the Bose T3 and be gPTP grandmaster. Stream-format/SRP details and the chime/turn-signal relay are unproven and safety-relevant. For a first cut, the analog/USB-DAC-into-amp fallback is far lower risk; escalate to real AVB only after a bench capture of the A11-T3 stream.
- **Panel/touch:** preserving the OEM FPD-Link III panel is the higher-risk half: bespoke serializer integration for fit/finish, and the panel is physically dash-integrated (~13.4" 2400x960 shaped module). Unless dash fit is a hard requirement, the far simpler path is a commodity touchscreen driven natively by the Pi (DSI/HDMI + USB/I2C touch), abandoning the OEM panel interconnect. Reuse the OEM panel only if you accept custom FPD-Link III bridge hardware. Touch alone is easy; video is where the engineering risk concentrates.
