1. EXECUTIVE SUMMARY
================================================================================
The GM AAOS infotainment system uses a VIP MCU (Renesas RH850/F1K) as security
gatekeeper. The VIP reads configuration from an M24C64 I2C EEPROM (8KB; full map ->
ELA) and controls Android system behavior including ADB authentication (PROTOKEY),
power management, 30+ system calibrations, ECU diagnostics/programming
authorization, and boot-sequence coordination with the GHS hypervisor.

KEY FINDINGS OWNED BY THIS DOC:
  [1] Security flags at 0x0440/0x0A80 are OUTSIDE CRC-protected regions [C] -- see
      Section 2.
  [2] DPS CANNOT write EEPROM security addresses directly [C] -- see Section 4.
  [3] I2C buses /dev/i2c-0 and /dev/i2c-1 are WORLD-ACCESSIBLE [C] -- see Section 3.
  [4] CRC is NOT ENFORCED AT BOOT (empirically verified) [V] -- see Section 2.4.
  [5] VIP_BOOT is unsigned but has internal Harman-checksum validation [C] -- see
      Section 6.

KEY FINDINGS POINTERED OUT (owned elsewhere, not restated here):
  [6] VIP controls ADB via seed response (0xFF = bypass, real ECUID = secured) -> GSK.
  [7] 30+ calibration values read from EEPROM control system behavior -> CVC.
  [8] IS25LP016 SPI flash (2MB) identified on board, secondary storage -> ../../platform/hardware_specs.md.
  [9] OTA/SPS updates can restore EEPROM values (resets security flags) -> ELA /
      ../../platform/ota_programming_roles.md.

2. CRC PROTECTION ANALYSIS
================================================================================

2.1 CRC LOCATIONS
------------------
| Address | Name           | Value       | Covers                     |
|---------|----------------|-------------|-----------------------------|
| 0x16E0  | Primary CRC    | 0xE2890000  | Main config (0x0398-0x07FF) |
| 0x19E0  | Secondary CRC  | 0xF1890000  | Backup config                |
| 0x1A80  | Config CRC     | 0x00000107  | Feature flags                |
| 0x1B40  | Data CRC       | 0x128A0000  | Calibration tables            |
| 0x1B60  | Block CRC #1   | 0x00000001  | Block validation              |
| 0x1B80  | Block CRC #2   | 0x00000001  | Block validation              |

(Full EEPROM region/purpose table for these address ranges: see ELA.)

2.2 CRC-PROTECTED vs UNPROTECTED REGIONS
-----------------------------------------
CRITICAL FINDING [C]: security flags are UNPROTECTED by CRC.

UNPROTECTED (no CRC recalculation required to modify):
  - 0x0000-0x005F: Header/boot flags
  - 0x0400-0x045F: PRIMARY SECURITY FLAGS (ADB bypass)
  - 0x0800-0x0A7F: Reserved/padding
  - 0x0A80-0x0AFF: BACKUP SECURITY FLAGS (ADB bypass)

CRC-PROTECTED (require CRC recalculation):
  - 0x0398-0x03BF: Module IDs
  - 0x0460-0x07FF: Radio/Audio/VIN data
  - 0x0E00-0x15FF: Display/Audio calibration tables

2.3 WHY THE ADB BYPASS ESCAPES CRC
------------------------------------
The security flags at 0x0440 and 0x0A80 fall BETWEEN CRC-protected regions:
  - Primary CRC (0x16E0) covers 0x0398-0x07FF BUT NOT 0x0400-0x045F.
  - The security block uses 0x5A framing (security type); see ELA for the full
    framing-byte catalog -- note framing/marker bytes vary by firmware build, so
    locate each security byte by OFFSET, not by marker value (ELA, History).
  - VIP reads these directly without CRC validation: checks the frame byte,
    reads the value byte, does not check against any CRC.

2.4 EMPIRICAL CRC TESTING RESULTS [V]
----------------------------------------
TESTED: VIN field (0x5C0-0x5D1) set to all 0xFF.
RESULT: module still booted into AAOS normally -- no factory reset, no boot
        failure, no observable behavior difference.

IMPLICATIONS:
  1. CRC is NOT enforced at boot time.
  2. CRC may only be validated during specific operations (OTA/SPS programming,
     DPS calibration writes, dealer service modes) -- untested which.
  3. More EEPROM regions are likely modifiable without CRC recalculation than
     the protected/unprotected split above implies.
  4. The "CRC-protected" designation may describe data-integrity-during-
     programming, not boot-time validation.

REVISED UNDERSTANDING:
| Region Type             | Boot Validation | Programming Validation |
|--------------------------|-----------------|-------------------------|
| Security flags (0x0440)  | NONE [V]         | Unknown                 |
| VIN (0x5C0)               | NONE [V] (tested)| Likely CRC-checked      |
| Calibration tables        | NONE [inferred]  | Likely CRC-checked      |
| Feature flags             | NONE [inferred]  | Unknown                 |

This significantly expands the safe-modification space for experimentation
relative to what the CRC-protected/unprotected table alone implies.

3.2 OPEN RESEARCH QUESTIONS [U]
----------------------------------
If the M24C64 EEPROM is on i2c-0 or i2c-1, software modification may be possible
without physical chip access. Still open (not answered elsewhere in this corpus
as of this pass):
  1. Which I2C bus connects to the EEPROM.
  2. EEPROM I2C address (likely 0x50-0x57; also open at ELA's §2.1).
  3. Whether SELinux blocks I2C access from a shell context on this specific
     device node even with world device permissions (see 3.4).
  4. Whether i2cdetect/i2cget/i2cset are present/usable to test (3).

Impact if answered favorably: could enable a SOFTWARE-ONLY bypass without
hardware (desolder) modification.

3.4 SELINUX GATING [C]
-------------------------
Even with world-accessible device nodes, SELinux may block access.
  Check with: `ls -laZ /dev/i2c-*` -- expected label `u:object_r:i2c_device:s0`.
  Shell access to `i2c_device` requires a shell-domain allow rule.

CORRECTED 2026-08-25: no stock build runs SELinux permissive (identical
enforcing init across builds; ../security/KERNEL_CVE_ANALYSIS.txt Appendix E.8,
also consolidated at ../../platform/security.md). I2C access is SELinux-gated on
ALL stock builds including Y177 and Y181 -- the original v1.1 text's
"permissive mode" escape hatch for this bypass does not exist on stock
firmware. From a stock shell, `i2cdetect` is SELinux-blocked on all builds
(folds the original Priority-1 research step; see History below).

History: this section's original body (v1.1, 2025-12-28) speculated SELinux
permissive mode as a possible way around the gating; a 2026-08-25 review note
corrected this in place (no stock build is permissive) and is now the only
standing claim -- the superseded speculation is not carried forward.

4. DPS CAPABILITIES AND LIMITATIONS
================================================================================

4.1 WHAT DPS CAN DO
----------------------
READ OPERATIONS [C]:
  - Read DIDs ($22 service): $F090, $F098, $F099, $F0B4, $F0F0, etc.
  - Read VIN, serial numbers, module IDs, ECU software versions, calibration
    identifiers, DTCs from all ECUs, ECUID from VIP ($F0F3).
  - Request security seed ($27 service) -- exchange detail owned by GSK.

WRITE/FLASH OPERATIONS [C]:
  Flash UNSIGNED modules (Sign Type = NONE):
    Module 23 SOC_BOOT, 24 SOC_UTILS, 28 SXM, 29 GPS, 51 TUNER, 52 ETH_SWITCH,
    55 SOC_ACPIO, 56 SOC_VBMETA (breaks AVB), 57 SOC_PRODUCT, 71 VIP_BOOT (*),
    72 SOC_ABL (*).
    (*) VIP_BOOT and SOC_ABL have internal validation despite carrying no TSS
    signature -- see Section 6.
    (Module 72 naming -- "SOC_ABL" here vs "SOC_BOOT" per live-radio
    moduleinfo -- is PLAN.md Open Conflict #2, owned by GM_INFO37_BOOT_CHAIN_ANALYSIS.md
    and ../../platform/ota_programming_roles.md's Open Conflicts; not re-litigated here.)
  - Create SPAT archives for programming.
  - Attempt version downgrades (version check disabled at the DPS layer).
  - Clear/modify calibration data via DID writes; execute routine controls
    ($31 service).

4.2 WHAT DPS CANNOT DO
-------------------------
EEPROM DIRECT ACCESS [C]:
  - CANNOT write to EEPROM security addresses (0x0440, 0x0A80).
  - CANNOT access EEPROM via I2C directly.
  - No UDS service exposes EEPROM write.
  Evidence: DPS uses UDS, which routes through VIP; VIP does not expose EEPROM
  write services via UDS.

CRYPTOGRAPHIC OPERATIONS [C]:
  - CANNOT issue SBAT tickets without GM authorization.
  - CANNOT generate security keys (requires GM TSS server).
  - CANNOT flash TSS-signed modules without GM keys.
  - CANNOT bypass AVB protection.

OTHER LIMITATIONS [C]:
  - CANNOT access fastboot mode (not exposed) or Android recovery (GHS owns
    recovery, not Android recovery -- see GBUR).
  - CANNOT modify the GHS hypervisor directly or unlock the bootloader.

4.3 DPS PROTOCOL FLOW
------------------------
```
DPS/TIS2WEB --> MDI2 (J2534) --> GMLAN/LS-CAN --> Gateway (0x45)
                                                      |
                                              +-------+-------+
                                              |               |
                                         VIP (0x80)    Other ECUs
                                              |
                                      SPI-IPC to SoC
```
The critical limitation: DPS commands reach the EEPROM only via VIP over UDS,
and VIP firmware does not expose EEPROM write commands over that path. (SPI-IPC
channel detail: ../../platform/vip_ipc_ghs.md. MDI2 wire-protocol detail: MDP.)

Two PLC timer values and two Key IPC Messages are not carried by
../../platform/vip_ipc_ghs.md's table despite that doc being this section's
pointer target, so they are kept here: PLC timers Tx PN Deactivation Timeout
= 300 ms and Emergency Unmount Timeout = 100 ms; Key IPC Messages
IPC_ID_RequestStartup (power up) and IPC_ID_NotifyAlarmStatus (wake timer).

6. VIP FIRMWARE MODIFICATION & RESEARCH PRIORITIES

6.1 VIP_BOOT FIRMWARE-PATCH ATTACK PLAN (Module 71) [research needed]
-------------------------------------------------------------------------
VIP_BOOT is flashable via DPS (Section 4.1) despite internal validation:
  - Harman checksum (proprietary algorithm)
  - SHA-256 message digest (cv_Act_Library)
  - Application signed-header validation
  - SBA/SBAT ticket validation
  - HDLC CRC protection

Unexecuted attack approach:
  1. Reverse engineer the Harman checksum algorithm.
  2. Patch VIP_BOOT to always read security flags as 0xFF, or always return an
     0xFF seed regardless of EEPROM state.
  3. Recalculate checksum; flash via DPS `update_ecu(71, ...)`.

Feasibility: MODERATE -- checksum algorithm unknown, signed-header validation
may block, no hardware fuse protection (unlike Intel ABL/CSE, 6.2).

History: the companion question this doc originally raised here -- whether the
VIP_APP seed/ADB-auth validator at 0x000b67d0 is a full validator or a "4-byte
stub" in Y177 specifically -- is ANSWERED by VIP_FIRMWARE_Y177_Y181_COMPARISON.md
(VFC, carried unchanged, v2.0, 2026-08-25): the function is a full ~906-byte
validator in Y175/Y177/Y181 alike; the stub claim was a fixed-absolute-address
misread of shifted/recompiled code and is RETRACTED. No VIP firmware difference
exists between builds here; the EEPROM SBI gate (this doc) and the validator
(VFC) gate ADB/seed auth the same way on Y177 and Y181 -- SELinux runtime mode
is an OS-side (ramdisk/init) matter, unrelated to this gate. See VFC §2 for the
binary diff; cited here, not restated.

6.3 CALDEF SCOPE BOUNDARY
----------------------------
CalDef (the Android-side calibration database) does NOT affect VIP-controlled
ADB security: `DEVICE_REGISTRATION_ENABLE_CHECK_OVERRIDE`,
`EXPIRATION_ENFORCEMENT`, and `GIS763_PROGRAMMING_ENABLED` only affect
Android-side registration/programming. VIP-controlled security (EEPROM flags,
seed/MEC/SBAT) is a separate system. Full CalDef security-relevant-entries
table: CALDEF_VIP_CALIBRATION_ANALYSIS.txt (CVC) -- pointer only.
