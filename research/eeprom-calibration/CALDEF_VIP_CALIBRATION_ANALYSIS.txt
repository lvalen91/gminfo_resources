1. EXECUTIVE SUMMARY
================================================================================
The GM AAOS system has two architecturally separate calibration systems:

  1. CalDef database calibrations -> Android/SoC software (Palto).
  2. VIP firmware calibrations -> VIP MCU (RH850).

`[U]` No CalOvride entry in either audited calibration set sets an EEPROM
security-bypass byte, an SBI byte, or the MEC counter directly (2026-11-07
direct payload audit, below). This does not rule out an indirect
reinitialization triggered by an SPS session, a calibration sequence, or ECU
firmware — the owner has independently observed SPS-related EEPROM-bypass
resets, and package reconstruction / modified-calibration acceptance remain
unverified.

2026-11-07 — direct audit of the two cached A11 calibration sets `[V]`/`[U]`:
Each set holds 14 CSM CalOvride payloads (slots 02-0F): LTZ has 983
OverrideValue entries, High Country 984. Every entry's CalID matched the local
2023 GIS-646 CalDefs (the local CalDefs may differ in version from the
payload; a name/description search cannot exclude undocumented indirect
effects).

Slot 05 (LTZ CalID 87846416; High Country 85877786) includes:
- `DEVICE_REGISTRATION_ENABLE_CHECK_OVERRIDE` = false (both, version 1). SFS2
  calls this a development override for the MEC check that gates automatic
  device registration — it describes bypassing *that* check, not changing
  MEC/SBI/EEPROM. An ADB effect has not been demonstrated.
- `EXPIRATION_ENFORCEMENT` = true (both). Addresses certificate-expiration
  enforcement; its relationship to ADB authorization is unproven.
- `SECURITY_EVENT_LOGGING_ENABLED` = false (both). A logging-feature switch,
  not evidence of an SBI/MEC setter.

Slot 09 includes `VIN_RELEARN_EN` = true (both) — a vehicle theft-lock/VIN
learning control; its definition does not identify it as an SBI setter.

2026-11-07 — independent Windows DPS utility finding `[S]`/`[U]`: the
installed DPS archive `UDS_SetMecToZero_Radio.zip` is a generic programming
utility, not one of the audited CalOvride entries. Its table describes
writing radio MEC to zero if not already zero; its script selects ECU 80 and
contains read-F1A0, compare, and write-F1A0 operations, with a one-byte-00
routine table. Static examination of the `pp.dll` interpreter supports the
candidate wire sequence `read 22 F1 A0`, conditional `write 2E F1 A0 00`. This
is a static inference, not a captured or attempted write; session/security
requirements, acceptance, EEPROM persistence, and relationship to ADB are all
unverified. The existence of a zeroing operation does not establish that a
nonzero inverse is accepted. See MDI2_RAW_UDS_BYPASS_GUIDE.md (carried
unchanged) for the Windows UDS path.

Note on wording: DPS_AND_MODIFICATION_LANDSCAPE.txt phrases the VIP-side
EEPROM-bypass finding as "bypass" where earlier drafts of this doc said
"enabled" — same effect (ADB enabled = the VIP-side check is bypassed), not a
contradiction. Both docs now point to ELA (§6.1 below) as the canonical
mechanism description; neither restates the byte-level detail.

```
|  | VIP Calibrations          |   | Security Functions         |   |
|  | (cal_vin_relearn_en, etc.)|-->| - PROTOKEY/ADB auth        |   |
|  | Stored in: VIP Flash/NVM  |   | - EEPROM flag checks       |   |
|  | Access: DPS flash only    |   | - Boot security            |   |
|  +----------------------------+   +----------------------------+   |
|              |                                                     |
|              v                                                     |
|  +----------------------------+                                    |
|  | EEPROM (M24C64)           |   (byte-level map, flag identity, |

```

Implication: CalDef calibrations like `DEVICE_REGISTRATION_ENABLE_CHECK_OVERRIDE`
affect Android software behavior (the MEC check bypass gating automatic device
registration) but do not touch VIP's EEPROM security-flag validation. ADB
authentication is handled by VIP firmware reading EEPROM flags via I2C and
relaying state to the SoC — this is architecturally independent of CalDef; the
exact mechanism is owned by ELA (§6.1 below), not restated here.

3.0 CALDEF RECORD STRUCTURE
----------------------------
Each calibration record has:
- CalID (unique identifier)
- Type (Boolean, Integer, String, Enumeration)
- Default value
- Reference (GIS specification)
- Usage (LOW, MID, HIGH, GLOBALA, GLOBALB, VCU, etc.) — indicates which
  vehicle/radio tier uses the calibration, NOT which Module ID contains it.

CalDef limitations: CalDef files define WHAT calibrations exist; they do NOT
state which Module ID contains each calibration, the binary format of
calibration storage, how to construct valid `.cfx` files, or whether
calibrations are signed.

3.1 SECURITY-RELEVANT CALDEFS
-------------------------------
This table dedupes and supersedes the separate, overlapping CalDef table that
previously stood in GM_AAOS_SECURITY_RESEARCH_COMPENDIUM.txt §6.1 (now
retired; this is the sole surviving copy per the corpus's "pick one owner"
rule). All six files below were confirmed present in both source documents'
tables (entries differing only in presentation have been merged):

FILE: SFS2_SecurityExtensionsFRD.caldef
  DEVICE_REGISTRATION_ENABLE_CHECK_OVERRIDE
    Type: Boolean | Default: FALSE
    Effect: Bypasses MEC (Manufacturing Enable Counter) check for device
    registration. IF TRUE: device registration proceeds regardless of MEC
    state. IF FALSE: registration waits for MEC == 0. Intended for
    development only, FALSE in production. Scope: Android Palto software
    (NOT VIP). The CalDef documents device registration, not ADB
    authentication or an EEPROM write — whether changing this setting
    affects ADB has not been tested.
  EXPIRATION_ENFORCEMENT
    Type: Boolean | Default: TRUE
    Effect: Controls certificate-expiration validation (Android TCS
    library). IF FALSE: may accept expired certificates. IF TRUE: enforces
    certificate expiration (normal mode only).
  OCSP_CHECK_FREQUENCY
    Type: Integer | Default: 900 seconds | Range: 300-86400 seconds
    Purpose: OCSP certificate-status check interval.

FILE: SFS22_SecurityEventLoggingFRD.caldef
  SECURITY_EVENT_LOGGING_ENABLED
    Type: Boolean
    Purpose: Enables security-event logging to a back-office server.

FILE: GIS763_InfotainmentProg_GlobalB.caldef
  GIS763_Gateway
    Type: Integer | Default: 69 (0x45)
    Purpose: Diagnostic address of CGM (Central Gateway Module).
  GIS763_WAITING_FOR_SECURE_ACCESS
    Type: Integer | Default: 1000 ms | Range: 300-3000 ms
    Purpose: Timeout waiting for SecurityAccess unlock.
  GIS763_WAITING_FOR_SEED
    Type: Integer | Default: 1 second | Range: 1-10 seconds
    Purpose: Timeout waiting for SecurityAccess seed response.
  GIS763_WAITING_ON_SESSION_KEYS
    Type: Integer | Default: 3 seconds
    Purpose: Timeout for session-key response.
  GIS763_PROGRAMMING_ENABLED
    Type: Boolean | Default: TRUE
    Purpose: Master programming enable/disable switch. Scope: Android update
    subsystem.
  GIS763_SigningCertificateIssuer
    Type: String
    Default: "CN=GPD, OU=GMNA GPD PRODUCTION, O=GENERAL MOTORS LLC"
    Effect: Expected certificate issuer for signature validation.
  GIS763_SigningCertificateSubject
    Type: String
    Default: "CN=GM Code Signature Server, OU=GM NA INFOTAINMENT, O=GM"
    Effect: Expected certificate subject for code signing.

FILE: GIS363_InfotainmentProg_GlobalA.caldef
  PROGRAMMING_ENABLED
    Type: Boolean | Default: TRUE
  WAITING_ON_GMLAN
    Type: Integer | Default: 200 ms
    Purpose: CAN network response timeout.

    Type: Integer | Default: 4000 MB

4.2 VIP CALIBRATION STORAGE
-----------------------------
These calibrations are stored in VIP internal flash/NVM. They can only be
modified by:
1. Flashing new VIP_APP firmware via DPS (signed).
2. Potentially via VIP JTAG debugging (physical access).

DPS cannot modify these calibrations without replacing VIP firmware.

5.3 CRITICAL OBSERVATION
----------------------------
The SoC requests calibration data from VIP via IPC; VIP reads from its
internal storage and sends it to the SoC. This is a ONE-WAY flow (VIP ->
SoC) — the SoC cannot write calibration data back to VIP via this channel.

6.1 WHAT CONTROLS ADB ACCESS?
---------------------------------
Out of charter — this is the EEPROM/SBI/MEC/ADB-gating mechanism, owned
entirely by EEPROM_LAYOUT_COMPREHENSIVE_AUDIT.md (ELA) §0.10-0.14. Do not
restate the byte-level mechanism here; this section previously carried a
now-folded "original claim + CORRECTED 2026-09-26" errata pair (the original
claim that EEPROM 0x0440/0x0A80 "5A FF 5A" directly gates ADB, and that the
VIP PROTOKEY/$27 seed validator gates ADB, were both corrected as imprecise/
wrong by the 2026-09-26 pass against primary evidence — 7-dump byte compare,
RH850 disassembly, the adb-auth binary, and an ecu80_READ CAN capture). That
correction is now folded into ELA's own text; this doc keeps only the pointer.

Summary of the corrected picture (full detail and byte addresses in ELA, not
here): ADB is gated SoC-side. VIP reads the SBI byte, transmits the resulting
MEC value to the SoC via DID 0xF1A0, and SoC-side `gm_adb_auth_init` sets
`is_secure_mode` (MEC in [1,255] => bypass). The VIP PROTOKEY/$27 seed
validator does not gate ADB — see the MEC-semantics Open Conflict below for
the one point ELA/GSK/GBUR have not yet closed.

Seed/signature-format detail (UDS 27/67 exchange, seed length, CMAC
algorithm, container signature verification) is likewise out of charter — see
GM_SEED_KEY_AND_CALIBRATION_SIGNATURES.md (GSK).

6.2 WHAT CALDEF CALIBRATIONS AFFECT
---------------------------------------
| Calibration                               | Affects               | Does NOT affect |
|--------------------------------------------|------------------------|------------------|
| DEVICE_REGISTRATION_ENABLE_CHECK_OVERRIDE  | Device registration   | ADB auth         |

None of the examined CalDef calibrations affect ADB authentication, per the
CalOvride payload audit in §1 and the corrected EEPROM/ADB mechanism pointed
to in §6.1.

7. EXPLOITATION ANALYSIS
================================================================================

7.1 CAN DPS CALIBRATION FILES ENABLE ADB?
---------------------------------------------
ANSWER: NO. DPS calibration files (`.cfx`) modify Android/SoC calibrations;
these do not control VIP EEPROM access. Creating custom `.cfx` files cannot
enable ADB. (Consistent with the 2026-11-07 payload audit in §1, which found
no setter in the live CalOvride payloads either.)

7.2 CAN DPS MODIFY VIP CALIBRATIONS?
----------------------------------------
ANSWER: only via VIP firmware flash. VIP calibrations are embedded in
VIP_APP firmware. To modify them: extract VIP firmware, modify calibration
values, re-sign (requires GM signing keys — see GSK for the signing-trust
chain), flash via DPS. Without GM signing keys, VIP firmware modification is
blocked.

7.3 REMAINING ATTACK VECTORS
---------------------------------
1. Physical EEPROM modification `[U]` — unverified claim as stated in this
   doc's own prior draft ("proven working," no citation here); the actual
   I2C mechanism and any confirmed bypass are owned by ELA — do not treat
   this doc as the source for that claim.
2. Y177 firmware downgrade — SELinux-enforcing status corrected; see History
   below. Requires testing AVB rollback behavior (owned by
   GHS_DOWNGRADE_PROTECTION_ANALYSIS.txt).
3. VIP utility file reverse engineering — if DPS utility `.dll`/`.zip` files
   contain I2C opcodes, could potentially write EEPROM via DPS; requires RE
   of the utility format (see §1's `UDS_SetMecToZero_Radio.zip` finding).
4. VIP UART console — `/dev/ttyACM1` accessible; may accept debug commands;
   may require bypassing a 74LVC08A gate.
5. VIP JTAG — physical debug access; full firmware dump/modify; requires
   hardware probing.

History: this section originally stated "SELinux permissive in Y177" for
vector 2. Corrected 2026-08-25: stock Y177 downgrade yields ENFORCING, not
permissive (per the research corpus's SELinux-enforcing finding, now owned by
`platform/security.md`/GBUR — not restated here). The stale claim is removed;
only the corrected state is kept above.

OPEN CONFLICTS
================================================================================
These are not settled by this doc; they belong to the named owner's Open
Conflicts section and are listed here only because this doc's content
touches them.

1. MEC value semantics — whether a nonzero/244-style Manufacturer Enable
   Counter reading means "bypassed/unlocked" (VIP_CONTROL_ANALYSIS.txt §5.2,
   ELA, GHS_BOOT_UPDATE_RECOVERY_ANALYSIS.md §2.3.6-7's per-unit MEC table) or
   "production/locked" (retired docs). Not closed across any of the four
   docs that touch it. Owned by GSK and ELA's Open Conflicts — not this doc's
   to settle; the §6.1 mechanism summary above assumes the "bypass" reading
   used by GBUR's live-tested path, consistent with ELA/GSK, but the
   semantic rule itself remains open there.
2. EEPROM dev-flag byte, 0x0B40 vs 0x0B41 — referenced above in §8.1 item
   [2]; owned and (per the plan) settled in VCA, not here.
