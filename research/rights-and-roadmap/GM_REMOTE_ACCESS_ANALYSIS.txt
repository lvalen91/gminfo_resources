================================================================================
                         EXECUTIVE SUMMARY
================================================================================

GM vehicles with AAOS (Android Automotive OS) have multiple remote access
pathways that allow General Motors to:

  - Push firmware updates (potentially mandatory)
  - Access vehicle CAN bus remotely
  - Collect telemetry and security event data
  - Execute remote commands (start, lock, climate, etc.)

These capabilities exist through TWO independent systems:
  1. OnStar/Telematics Module (works WITHOUT the radio installed)
  2. A11 Infotainment Radio (AAOS)

BUS-2 DIRECT TAP (Y175, 2026-11-02 bench finding): a direct physical T1 tap on
Ethernet Bus 2 (A11 Radio <-> K56 gateway) confirmed a third VLAN not in the diagram
above -- VLAN 2 (PCP 2) carries AVB/TSN audio (IEEE-1722 AVTP, ~2,900 pps bench flood)
and gPTP, with no IP addressing of its own; it is a media-transport plane, not a
service/diagnostic plane. [V, bench tap]

Separately, this radio's internal bridge `br0` (192.168.5.1/24, members wlan1/wlan2) is
the Wi-Fi/phone-projection AP bridge serving DHCP+DNS to paired-phone clients -- it is NOT
a diagnostic or telematics plane, correcting any earlier reading of it as such. [V, bench]

An exhaustive full-port (1-65535) x full-source (/24) sweep of VLAN 5 and VLAN 4 from the
direct tap found exactly three reachable services and no undocumented listening port or
allow-listed identity anywhere in either /24:
  - 192.168.1.100:9016  NetworkAccessManager, source allow-list {.102, .112}
  - 192.168.1.100:9002  RemoteModuleHMI, source allow-list {.106, .109, .112}
  - 172.16.4.100:49156  diagnosticsd, source allow-list {.107, .112}
[V, bench sweep]

The "Port 2: CGM" switch-port labeling in the physical-layer diagram above is a separate
claim (physical switch port enumeration, not VLAN/bus identity) that this bus-2 tap
finding does not confirm or refute -- left as-is pending its own verification (Open
Conflicts, below). Full tap methodology: platform/ethernet_networking.md and
platform/avb_audio_transport.md (VLAN 2 / AVTP detail); bench provenance in the research
tree's ../../evidence/session-logs/ (not resolved by this reorg per the writer brief).

5.4 CALIBRATION FILE SECURITY RESET -- REFUTED, see History
------------------------------------------------------------
Originally reported: a calibration file (85783460, SW ID 07) was claimed to contain an
encrypted payload resetting EEPROM 0x0440/0x0A80/0x0B40 to re-lock security/backup/debug
flags, implying SPS calibration visits could silently reset owner EEPROM modifications.

REFUTED. [History: corrected 2026-11-12, per AUG24_25_DOC_REVIEW_CORRECTIONS_AUG2026.md
correction #1 -- the quoted byte range sits inside the gzip-compressed CalOvride XML
stream, not an EEPROM address:value table, and all 14 decompressed CSM cal files have
zero hits for "0440/0a80/0b40/eeprom/security/SBI/bypass". The owner-observed EEPROM-
bypass reset after SPS visits (AUG24_SESSION_FULL_PCAP_TIMELINE.md §5) is real, but this
file/payload was never its confirmed mechanism.] Current EEPROM address assignments and
the SPS-reset mechanism (if later identified) are owned by ELA, not this doc -- do not
reintroduce 0x0440/0x0A80/0x0B40 as a security-reset payload here.

            SECTION 9: GHS HYPERVISOR CAMERA/DISPLAY BYPASS
================================================================================

GM's A11 radio uses a GHS (Green Hills Software) INTEGRITY hypervisor that runs BELOW
Android, providing safety-critical functions independently of the OS. This section
covers only the camera/display-bypass angle; the hypervisor's own PCI/task/IPC
architecture and attack-surface catalog are owned by GIC (GHS_INTEGRITY_COMPREHENSIVE_
ANALYSIS.md) and platform/vip_ipc_ghs.md -- not restated here.

9.1 HYPERVISOR DEVICE INTERFACES
--------------------------------
GHS provides multiple device interfaces to Android:

+------------------------------------------------------------------+
| DEVICE PATH          | SELinux CONTEXT       | PURPOSE            |
+------------------------------------------------------------------+
| /dev/ghs/ipc         | ghs_device            | Inter-Process Comm |
| /dev/ghs/cal         | ghs_device            | Calibration        |
| /dev/ghs/chime       | ghs_device            | Audio Chimes       |
| /dev/ghs/camera      | ghs_camera_device     | Camera Access      |

9.2 CAMERA BYPASS ARCHITECTURE
------------------------------
FINDING: Backup camera works DURING Android reboot.

When Android reboots (adb reboot, steering wheel hold), the display shows the backup
camera feed if the vehicle is shifted into reverse. This indicates [inferred, from
observed reboot behavior, not a traced data-path capture]:

  1. GHS hypervisor continues running when Android restarts
  2. GHS receives CAN bus signals (gear position) independently
  3. GHS directly controls display overlay for camera feed
  4. Android EVS (External Vehicle Service) is a PASSTHROUGH, not the source

CAMERA DATA FLOW:
+------------------------------------------------------------------+
|                                                                  |
|  [Rear Camera] --> [Video Input] --> [GHS Hypervisor]            |
|                                           |                      |
|                                           | /dev/ghs/camera      |
|                                           v                      |
|  [CAN Bus: Gear Position] -------> [GHS Display Controller]      |
|                                           |                      |
|                                           | Direct Overlay       |
|                                           v                      |
|                                    [Display Panel]               |
|                                    /dev/ttyS3, /dev/i2c-7        |
|                                                                  |
+------------------------------------------------------------------+

9.3 EARLY EVS SYSTEM
--------------------
Binary: /vendor/bin/earlyEvs_harman (COMMENTED OUT in production)

SELinux capabilities of early_evs domain:
  - camera_device access (read/write)
  - video_device access (read/write)
  - gpu_device access (read/write)
  - display_panel_device access
  - can_socket access (CAN bus!)
  - serial_device access

The early_evs service was designed to provide camera during early boot BEFORE Android
fully starts. In production, this role is handled by GHS directly.

9.4 WHO ACCESSES GHS CAMERA?
----------------------------
SELinux policy shows these domains access ghs_camera_device:

  - gmConnectionService  (GM's main connection service)
  - system_app          (System applications)

This allows Android apps to request camera overlays via GHS when needed.

9.5 DISPLAY PANEL CONTROL
-------------------------
Display panel devices (/dev/ttyS3, /dev/i2c-7) are accessed by:

  - gmConnectionService
  - gm_update_engine
  - gm_vehiclepanel
  - early_evs
  - remote_display
  - system_app

This multi-layered access is consistent with GHS controlling the display independently
of any single Android component, though it is a permission-table reading, not a traced
runtime arbitration test.

9.6 SECURITY IMPLICATIONS
-------------------------
  - GHS continues operating when Android crashes or reboots
  - Camera feed is a SAFETY feature - must work without Android
  - GHS has direct hardware access, independent of Android's own security model
  - GHS could, in principle, display content on screen without Android's involvement
    [inferred -- no content-injection test performed; a capability reading, not an
    observed exploit]
  - CAN bus signals reach GHS before Android processes them

================================================================================
                      SECTION 10: KEY FINDINGS SUMMARY
================================================================================

1. GM has DUAL remote access paths (Telematics + A11 Radio)

2. Telematics module operates INDEPENDENTLY, per static analysis -- removing the radio
   does NOT disable remote vehicle control in the firmware/wiring model reconstructed
   here (not directly bench-verified; see section 6)

3. Red Bend Update Agent supports "(mandatory)" updates - potential
   for forced updates without user consent (string-level finding)

4. gmConnectionService has REBOOT permission - can restart device
   without user interaction

5. Security Event Logging is ALWAYS ON - telemetry constantly
   reports to vehicle.api.gm.com:20445

6. A11 and Telematics share internal Ethernet network - data can
   flow between them

7. GIS768_IgnoreCurrentPartNumberCheck = TRUE bypasses the part-number check on updates
   ONLY -- it does NOT enable a firmware downgrade. The actual anti-rollback is the GHS
   hypervisor's rollback counter in misc/vda9, which blocked a tested Y181->Y177 at boot.
   See section 4 above; mechanism detail in GDP/GBUR.

8. REFUTED (see section 5.4 History) -- there is no confirmed calibration-file security-
   reset payload acting as defense-in-depth against EEPROM modifications. The underlying
   SPS-visit EEPROM-reset observation is real; this specific mechanism claim is not.

9. Complete remote access chain (static reconstruction): Cloud -> Telematics -> Android
   Service -> Update Engine -> Red Bend -> Flash

10. No way to fully disable remote access without physical
    disconnection of telematics module

11. GHS Hypervisor operates BELOW Android, controlling camera and display directly -
    backup camera works even during Android reboot (section 9.2, inferred from behavior)

12. GHS has direct CAN bus access and can, in principle, overlay content on display
    independently of Android OS state (capability reading, not an observed exploit)
