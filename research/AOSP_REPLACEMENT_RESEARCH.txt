1. RESEARCH GOALS AND OBJECTIVES
================================================================================

1.1 PRIMARY GOAL
----------------
Replace GM AAOS entirely with a true AOSP Android Automotive implementation,
enabling full developer control over the infotainment system.

1.2 ALTERNATIVE GOAL
--------------------
If the GHS INTEGRITY hypervisor must remain for vehicle functions (turn
signal chimes, door sounds, camera access via CAN bus), enable GHS to boot a
generic or locally-compiled AOSP build as its Android guest VM.

1.3 SUCCESS CRITERIA
--------------------
- Custom AOSP image boots successfully
- Vehicle integration functions preserved (chimes, cameras, CAN messages)
- ADB access without GM restrictions
- SELinux configurable (permissive or custom policy)
- No dependence on GM signing infrastructure

1.4 ACCEPTABLE TRADE-OFFS
--------------------------
- GHS hypervisor remains if required for vehicle safety functions
- VIP firmware unchanged if it doesn't block custom Android
- Some GM services may need reimplementation

1.5 CURRENT STATUS OF THE STATED GOAL (added on consolidation)
----------------------------------------------------------------
The §1.3 success criterion "no dependence on GM signing infrastructure" is, as
of the latest dated findings folded into §4 below, blocked end-to-end by
software means: both ELK fastboot-unlock gates are closed (§4) and no software
path to flip either is known. The remaining paths are hardware-level (VIP
JTAG/glitch, chip-off) — see §7. This doc never stated that scope-level
conclusion outright in the original text; it is stated here explicitly so the
roadmap in §7-§8 is read against the real current blocker, not the original
Dec-2025 optimism.

4. BOOT CHAIN AND SIGNING REQUIREMENTS
================================================================================

4.1 Boot sequence, signing hierarchy (VIP -> Intel ABL -> GHS INTEGRITY ->
Android/AVB), and AVB GSI pubkeys (q-gsi/r-gsi/s-gsi) are owned by
`platform/boot_chain.md`. This doc does not restate the 10-step sequence or
the 4-level signing table; see that doc for the full detail.

4.2 ELK / OEM-UNLOCK STATUS (summary; full mechanism in platform/elk_recovery.md)
-----------------------------------------------------------------------------------
ELK (Intel ABL / "SOC_ABL", module 85738845) is Intel Kernelflinger fastboot
with AVB verification active; `fastboot flashing unlock` is gated by
device-state, same as stock Android. There is no external-USB-rootfs path
through it. The realistic custom-OS chain is: reach ELK -> flip
`oem_unlock_allowed` (currently 0) -> `fastboot flashing unlock` (currently
BLOCKED on step 2) -> flash unsigned images. Both gates are OPEN/unresolved;
no software path from this OS is known to flip either. [C] 2026-10-08
binary trace confirms the lock state is read from the UEFI NV variable
`OEMLock` (GUID `1ac80a82-4f0c-456b-9a99-debeb431fcc1`) via
`read_device_state_efi()`, is not Boot-Guard-hashed (BPM.met covers IBBL/IBB/
OBB code only, not the NVRAM varstore), and is not TPM2/RPMB-backed per static
trace of SOC_ABL — whether the varstore is SPI-NOR (offline-settable) or
RPMB-backed (replay-protected) is the decisive open physical question. Full
binary-RE detail (offsets, BPM.met findings F1/F2/F4, TXE FPF/OTP caveats) and
the live-tested ELK-trigger mechanism are owned by `platform/elk_recovery.md`
and GHS_BOOT_UPDATE_RECOVERY_ANALYSIS.md (GBUR) §2.3.2/§2.3.7 respectively —
see those docs, not this summary, for anything beyond the "both gates closed,
no software path" conclusion this roadmap depends on.

4.3 GSI/DSU STATUS
-------------------
Developer Options exposes a DSU Loader / GSI section, but it is non-functional.
History: original Dec-2025 text guessed five possible causes (SELinux
enforcement, update_engine permissions, network block, GHS/DSU incompatibility,
insufficient /data space) — all superseded. The confirmed root cause
(2026-09-03, live OS dump): `com.android.dynsystem`, the DSU front-end app, is
absent from the live 89-package set; the Developer-Options DSU Loader and the
`am start-activity -n com.android.dynsystem/...` intent path fail with
activity-not-found, not a policy denial. `gsid`/`gsi_tool` are retained with
full stock SELinux policy (block is not at the policy layer); the direct
`gsi_tool` path is closed by the user build (`ro.debuggable=0`, shell uid
2000, `MANAGE_DYNAMIC_SYSTEM` signature|privileged permission); and booting
any staged GSI is separately gated by locked verified boot
(`flash.locked=1`, `device_state=locked`, `verifiedbootstate=green`,
`sys.oem_unlock_allowed=0`), with fstab trusting only Google GSI keys (q/r/s).
Canonical/full provenance: `platform/boot_chain.md` §GSI/DSU Status; this is a
summary copy, not the owner.

4.4 VBMETA / ROLLBACK
-----------------------
vbmeta holds the anti-downgrade rollback index, hash descriptors, and
verification public keys. A hypothetical AVB bypass (custom signing key or
disabled verification mode) would not, by itself, enable a Y181->Y177
downgrade: the GHS hypervisor enforces its own independent rollback counter
in `misc`/vda9 (not vbmeta) and rejects an older image at boot regardless of
AVB state. Both vbmeta.rollback_index values are 0; the GHS counter is the
actual enforcing gate. Full downgrade-mechanism detail, including the GHS
rollback-counter implementation and the live downgrade test, is owned by
GHS_DOWNGRADE_PROTECTION_ANALYSIS.txt (GDP); do not restate it here (see §7.2
History below for how this affects the roadmap).

5. VIP FIRMWARE MANIPULATION VECTORS
================================================================================
VIP (RH850) security responsibilities (ADB authentication via PROTOKEY/ICUSB,
EEPROM security-flag verification, power-state management, CAN comms with
BCM, IPC with SoC/GHS), the EEPROM SBI/MEC bypass mechanism, and the VIP
exploitation-vector list (UART console, DPS flash, JTAG, UDS CalDef override)
are owned by `platform/vip_ipc_ghs.md` (VIP role) and
EEPROM_LAYOUT_COMPREHENSIVE_AUDIT.md / `platform/eeprom_i2c_security.md`
(EEPROM mechanism, canonical per ELA §0.10-0.14). This doc's only retained
fact: the EEPROM/ADB bypass's ceiling is relevant to the roadmap because it
caps what §7's "GSI boot test" / vector-1 path can reach even if successful —
the bypass tops out at Android-guest `uid 2000` (no known EEPROM path to
root), so CSM boot ownership for a custom-AOSP replacement still needs either
the T1/DoIP-to-VIP path or the ELK/fastboot unlock chain in §4.2, not USB adb.
See ELA/`platform/eeprom_i2c_security.md` for the address-level mechanism and
the 2026-09-26 correction (ADB gating is SoC-side MEC/`is_secure_mode`, not
seed-consuming) — not restated here.

Potential VIP firmware modifications that would enable a custom-AOSP boot
(disable GHS signature-verification IPC, always report "authenticated" for
PROTOKEY, allow an unsigned boot chain, pass through boot control without
validation) remain unexplored hypotheses pending VIP JTAG access (§7.3).

-------------------------------------

For a custom AOSP replacement, the following would need reimplementation:
1. Vehicle HAL (reimplementation, or use the generic VHAL)

7. ATTACK SURFACE PRIORITIZATION
================================================================================
This section and §8 are this doc's unique contribution to the corpus — no
`platform/` doc owns attack-surface prioritization or a phased research
roadmap for the AOSP-replacement goal specifically.

7.1 HIGH PRIORITY VECTORS
----------------------------
1. GSI BOOT TEST (HIGHEST)
   AVB trusts GSI keys (q/r/s-gsi); test whether a stock Android GSI boots.
   If successful, provides an immediate custom-AOSP path. The realistic
   general chain, however, is the ELK/fastboot `oem_unlock` path in §4.2
   (ELK -> `oem_unlock_allowed` -> `fastboot flashing unlock` -> flash
   unsigned); both gates are currently open/unresolved — this is an
   assessment, not a solved path.

2. GHS PARTITION ANALYSIS (HIGH)
   Dump `ghs_isys_a`/`_b`, analyze VM configuration, find signature
   verification code (feeds GIC's §11 attack-surface question, not restated
   here).

7.2 MEDIUM PRIORITY VECTORS
-------------------------------
3. VBMETA MODIFICATION — attempt to disable AVB verification; would allow
   unsigned Android images (does not, by itself, unblock a Y177 downgrade —
   see §4.4).
4. VIP UART EXPLOITATION — access the debug console; may reveal a security
   bypass.
5. GHS_LOG ANALYSIS — may contain boot debug info revealing the VM-loading
   process.

Y177 DOWNGRADE — RETIRED VECTOR
History: originally ranked HIGH priority on the theory that "version check
confirmed disabled" at write time would let an inactive-slot Y177 image boot,
unlocking further exploration. Corrected 2026-08-25 and reconfirmed on live
test: stock Y177 boots SELinux-enforcing, so even a successful downgrade
would not grant permissive access (security/KERNEL_CVE_ANALYSIS.txt Appendix
E.8). Separately, the "version check disabled" flag affects only the
inactive-slot WRITE phase — the GHS hypervisor's independent rollback counter
(in `misc`/vda9, not vbmeta) blocks the downgrade at boot regardless, and this
was confirmed FAILED on test. This vector is DEAD; demoted out of the active
roadmap. Full downgrade-mechanism detail: GHS_DOWNGRADE_PROTECTION_ANALYSIS.txt
(GDP); live boot-chain evidence: GHS_BOOT_UPDATE_RECOVERY_ANALYSIS.md (GBUR).

7.3 RESEARCH VECTORS (LONG TERM)
------------------------------------
6. VIP JTAG DEBUG — full firmware extraction, complete security-model RE.
7. GHS INTEGRITY RE — understand VM signing, find a verification bypass.
8. CUSTOM GHS VM IMAGE — create an unsigned VM definition, boot custom AOSP
   under GHS.

# Dump partition (requires root or permissive SELinux)
dd if=/dev/block/vda1 of=/sdcard/ghs_isys_a.img bs=4096

# Check AVB status
avbtool info_image --image boot_a.img

# Extract vbmeta
dd if=/dev/block/vda10 of=/sdcard/vbmeta_a.img bs=4096

# Check GHS log
cat /dev/block/vda24 | strings | less

# List partitions
ls -la /dev/block/by-name/

# Check for GSI compatibility
getprop ro.product.first_api_level
