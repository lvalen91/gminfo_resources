1. EXECUTIVE SUMMARY
================================================================================

DOWNGRADE ATTEMPT: Y181 -> Y177 (and, per the 2026-08-25 addendum, Y181 -> Y175)
RESULT: BLOCKED, both directions. [C] field-observed, repeated bench testing,
own unit (2026-08-17 re-test, §2.2 below).

WHAT IS CONFIRMED: a lower-version USB update package is rejected and the
active Y181 slot is left unmodified. Same-version reinstall and upgrades both
succeed, which isolates the block to a version/rollback-index check rather than
a signature, packaging, or USB-media problem (§2.2).

WHAT IS NOT CONFIRMED, AND CONTESTED WITHIN THIS DOC'S OWN HISTORY: exactly
*where* the rejection happens and by what mechanism. The original 2024-12-30
account (§2.1) describes a full partition write to the inactive slot followed
by a post-write GHS boot-time AVB/rollback-verification revert. The 2026-08-17
owner re-test (§2.2) instead observed a version-gated rejection that, on normal
boot, never even prompts, and in recovery mode fails early (progress bar starts,
then "update not supported / invalid") — consistent with an early reject at
update/write time rather than a full write-then-revert. This document's own
Conclusions (§9, formerly "11.1 CONFIRMED FINDINGS") never reconciled the two
models and continued to assert the original post-write-verification account
after the re-test contradicted it. This is carried as Open Conflict #1 below
(= consolidation-plan Open Conflicts item 8) rather than silently resolved.

The manifest's "version check disabled" flag only affects `gm_update_engine`'s
write phase (Android side); it does not disable whatever check performs the
actual rejection — GHS boot-time AVB/rollback verification under the original
model, or an earlier version-gate under the re-test's model (§3, §6.1).

3. GHS INTEGRITY AS VERIFICATION GATEKEEPER
================================================================================

3.1 TWO-PHASE MODEL (write vs verify)
-------------------------------------------------------------------------------
As originally stated, the update mechanism is modeled as two phases:

PHASE 1 — WRITE (`gm_update_engine` in Android): reads the manifest from USB,
writes raw partition images to the inactive A/B slot. "version check disabled"
in the manifest means no version check in this phase — it is a "dumb pipe,"
does not reject or verify based on version.

PHASE 2 — VERIFY (GHS INTEGRITY, modeled as happening at boot): GHS loads
before Android, performs AVB verification, checks the rollback index against a
stored value, rejects boot on failure, falls back to the original slot.

This two-phase separation ("write anything, GHS decides if it boots") is the
original 2024-12-30 explanation for why "version check disabled" doesn't defeat
the block (§6.1 original). It remains a reasonable account of the *write* phase
(confirmed: the write phase itself is version-blind) but §2.2's re-test shows
the *rejection* can occur before a full write-and-boot cycle, which this
two-phase framing does not by itself explain — see Open Conflict #1.

3.2 GHS PERFORMS AVB VERIFICATION (evidence: binary strings)
-------------------------------------------------------------------------------
Evidence from GHS binary (85098662, GFM-owned byte map) string analysis [S]:

    VMM: Error: vbmeta signing key does not match known valid key
    VMM: vbmeta: image verification failed!
    VMM: %s: no signed boot partition in vbmeta.
    Android image failed verification: verity disabled?

These strings establish that GHS validates vbmeta before starting the Android
guest; they do not by themselves establish *when* in the update flow that
validation first has an effect (see §2.2, Open Conflict #1).

3.3 GHS SLOT MANAGEMENT (evidence: binary strings)
-------------------------------------------------------------------------------
    GHS: Android and INTEGRITY slot mismatch.  INTEGRITY: %s Android: %s Rebooting...
    GHS: [LIFECYCLE] Android failed to boot (count=%lu)

GHS maintains its own slot state and boot-failure counting; on slot mismatch or
boot failure it initiates recovery.

================================================================================
4. ROLLBACK PROTECTION MECHANISM
================================================================================

4.1 GHS HAS AN EXPLICIT ROLLBACK CHECK (evidence: binary string)
-------------------------------------------------------------------------------
GHS binary offset 0x00cf85ac (`.vmm1.rodata`):

    VMM: ERROR: rollback index is too old: %lu in image, but stored is %lu

Confirms GHS: (1) reads a rollback index from the vbmeta image, (2) compares it
against a STORED rollback index, (3) rejects when image index < stored index.
[S] string-level, not disassembled — see Open Conflict #2.

4.2 ROLLBACK INDEX STORAGE: MISC PARTITION — hypothesis, not disassembled
-------------------------------------------------------------------------------
The stored rollback index is modeled as living in the misc partition (vda9),
based on these strings:

    VMM: ERROR: failed to read A/B metadata from 'misc'
    VMM: Warning: A/B metadata: magic number mismatch
    VMM: ERROR: A/B metadata: version on disk too new
    VMM: A/B metadata updated
    VMM: ERROR: Android boot requires misc partition

Partition mapping: misc = /dev/block/vda9; holds the A/B bootloader-control
structure; the stored rollback index is presumed to live inside it and be
updated by GHS after a successful boot. [inferred] — the exact structure was
never disassembled (Open Questions, §9).

4.3 VBMETA ROLLBACK_INDEX IS FLAT 0 ACROSS RELEASES
-------------------------------------------------------------------------------
Both Y177 and Y181 vbmeta files have rollback_index = 0 at offset 0x70:

    Y181 vbmeta (86331644): 0000 0000 0000 0000
    Y177 vbmeta (86283158): 0000 0000 0000 0000

(Extended by the 2026-08-25 addendum to Y175 = 0 as well — §5.) This means the
AVB `rollback_index` field does NOT encode version ordering; GHS must be
maintaining its own counter elsewhere (misc, §4.2) independent of this field.

4.4 PROPOSED ROLLBACK MECHANISM (hypothesis diagram)
-------------------------------------------------------------------------------
    ┌─────────────────────────────────────────────────────────────────────┐
    │  misc partition (vda9) — persistent storage                         │
    │  A/B metadata structure containing: magic number, version field,    │
    │  stored rollback index (GHS's counter), CRC checksum, per-slot boot │
    │  attempt counters                                                   │
    └─────────────────────────────────────────────────────────────────────┘

    Boot flow (hypothesis):
    1. GHS reads A/B metadata from misc
    2. Loads vbmeta from the target slot
    3. Compares vbmeta.rollback_index against stored_rollback_index
    4. If vbmeta.rollback_index < stored_rollback_index: "rollback index is too
       old"; increment boot-failure counter; after max failures, fall back to
       the original slot
    5. If verification passes: boot Android; on success, update
       stored_rollback_index in misc

[inferred]. This is one candidate mechanism for the *original* (§2.1) write-
then-revert model. It is not the only model consistent with the evidence —
§2.2's early-reject observation is also consistent with an equivalent check run
earlier in the flow. Not disassembled either way (Open Conflict #1, #2).

4.5 WHY REINSTALL WORKS BUT DOWNGRADE FAILS (theory)
-------------------------------------------------------------------------------
Theory: GHS's stored rollback value tracks version, not the (flat-0) AVB
rollback_index field:
- After Y181's first boot: stored_rollback reflects the Y181 version.
- Y181 reinstall: GHS sees same/equal version -> allow (same-version may be
  special-cased).
- Y177 downgrade: GHS compares Y177's version against the Y181-derived stored
  value -> reject ("rollback index is too old").

The exact comparison method (version string, build number, numeric field) is
unclear; see Open Questions, §9.

5. Y175 EXTENSION AND BUILD-VARIANT IDENTITY (addendum, 2026-08-25)
================================================================================

Scope: extends §4 to Y175, and settles whether Y175's board is the same
hardware as Y177/Y181.

A) Y175 DOWNGRADE / ANTI-ROLLBACK — confidence HIGH on the AVB facts, MEDIUM on
   the downgrade verdict (GHS HOSTOS compare logic itself not disassembled)

All three SOC_VBMETA images parsed (AVB0, libavb 1.0, avbtool 1.2.0,
alg=1/SHA256-RSA), no chain-partition descriptors in any of them:

    AVB rollback_index           : Y175 = 0   Y177 = 0   Y181 = 0
    AVB rollback_index_location  : Y175 = 0   Y177 = 0   Y181 = 0

The AVB rollback_index does not encode the Y175<Y177<Y181 ordering — it is flat
0 across every release (confirms and extends §4.3). Embedded os_version = 12
for all three. Version ordering lives in the build fingerprint + security patch
level (SPL), which is monotonic increasing:

    Y175  W213E-Y175.5.2-SIHM22B-383.1  security_patch 2024-05-05
    Y177  W231E-Y177.6.1-SIHM22B-499.2  security_patch 2025-02-05
    Y181  W231E-Y181.3.2-SIHM22B-499.3  security_patch 2025-06-05

VERDICT: Y181 -> Y175 is blocked by the same mechanism as Y181 -> Y177, at least
as hard. The floor is not the AVB rollback_index (identical 0 everywhere); it is
GHS's own misc-partition counter per §4.2/§4.4. Since Y175 is an older version
than Y177, any comparison rejecting Y177 against a Y181-provisioned stored
counter rejects Y175 a fortiori. CANNOT CONFIRM without disassembling GHS
HOSTOS internals: the exact per-release integer and the precise comparison
(>, >=) — i.e. whether counter *equality* would ever permit a lateral move. The
AVB evidence only proves the floor is not in AVB.

B) BUILD-VARIANT W213E vs W231E — confidence HIGH (same hardware/board)

W213E (Y175) vs W231E (Y177/Y181) is a software build-line/tag token in
`ro.build.id`, not a different hardware/board SKU. Identifiers compared (Y175
extracted trees vs Y181 vendor partition 86331650):

8. SIGNING-KEY EXTRACTION AND FEASIBILITY
================================================================================

8.1 KEY ARCHITECTURE OVERVIEW
-------------------------------------------------------------------------------
The vbmeta signing key used for AVB is modeled as protected by layered hardware
security:

    Hardware Root of Trust (Intel CSE)
      - CSE IVB Root Key (fused), CSE Intel Fixed Root Key,
        CSE BXT IVB Integrity/Confidentiality Keys, rot.key, oem.key
        (GM's signing key), rpmb_key
    -> GHS INTEGRITY hypervisor
      - ELF section `.mr_r_mod_android_key` (NOBITS, empty in file; symbols
        __ghsbegin_mr_r_mod_android_key / __ghsend_mr_r_mod_android_key;
        key loaded from bootloader modules at runtime)
      - Error strings: "Android signing key boot module not found",
        "Signing key modulus mismatch", "Signing key exponent mismatch",
        "vbmeta signing key does not match known valid key"
    -> Android Verified Boot (vbmeta)
      - Contains PUBLIC key hash, not the full key; rollback_index = 0 in both
        Y177 and Y181; signed with "release-keys"

8.2 KEY STORAGE LOCATIONS
-------------------------------------------------------------------------------
1. SOC Bootloader (85738845, Intel IPK format) — CSE key-management structures,
   `ipk.` header.
2. GHS binary `.mr_r_mod_android_key` section — NOBITS, size 0x1000, virtual
   address 0x02201000; key loaded at runtime from bootloader modules; symbol
   names present, key data NOT in the binary.
3. Trusty TEE Keymaster — Android keystore (application keys), not the boot-
   verification key.

History: the original §10.3 ("key extraction feasibility") stated the public
key is "protected by hardware... cannot be read even with root access," citing
CSE-encrypted storage. §10.5 (this section) then extracted that same public key
in plaintext from the bootloader's `.oemkeys` ELF section with no CSE
involvement. These are not actually in tension once the key class is specified:
the PUBLIC key (non-secret by design, used only for verification) was always
extractable from the bootloader image; it is the PRIVATE signing key that
remains held off-device in GM's build infrastructure and is the thing §8.4
below concludes is infeasible to extract. The original §10.3 text conflated the
two; folded in place rather than carried as an open conflict, since the
public/private distinction fully resolves it.

8.4 FEASIBILITY CONCLUSION AND ATTACK SURFACE
-------------------------------------------------------------------------------
KEY EXTRACTION (of the PRIVATE signing key) IS NOT FEASIBLE VIA SOFTWARE:
private key never exposed on-device or in update packages (only the public key
and signatures are present); the public key is delivered via the Intel
multiboot protocol from the bootloader to GHS at boot ("Android signing key
boot module not found" = key not yet loaded into GHS, not "unreadable");
SOC_HOSTOS's own key section is NOBITS/empty.

Attack-surface options considered for forging signed images or bypassing the
rollback/signature check (all speculative/untested, [inferred] unless noted):

  A. Obtain GM's private signing key — held in GM's build infrastructure behind
     an HSM; not present on vehicle or in update packages. Infeasible without
     insider access.
  B. Compromise Intel CSE — hardware attack on the CSE subsystem; requires
     physical lab equipment; designed to resist this. Extremely difficult.
  C. Replace the public key on-device, or modify misc's stored rollback index —
     GHS validates CRC/magic on misc and the key is used elsewhere in the boot
     chain; tampering is expected to be detected. High risk of bricking.
  D. Find a vulnerability in the signature-verification code itself — would
     require disassembly of GHS's AVB-verification path; no vulnerability
     identified from string-level analysis alone. See VPF for the parser-level
     (TOCTOU/overflow) fuzz-target analysis of the related `.vmm1`/libavb port
     — a different, lower-level question than this section's key-handling
     model.
  E. Factory/dealer-level reset of the misc partition, if it clears the stored
     rollback index — untested; see Open Questions §9.
  F. Physical eMMC access, direct write to misc — bypasses GHS entirely at the
     hardware level; very invasive.
  G. Modify the GHS binary itself to skip the rollback check — GHS
     (`85098662`) is TSS-signed; cannot flash a modified version via the
     normal update path without breaking GM's signing chain.

Significance of the OEM public key, independent of the above: it lets a third
party verify the authenticity of existing GM-signed images; it does not permit
creating new signatures or modifying images.

Relevant binary strings (signing verification, certificate parsing, key-module
management) — catalogued once in §6.3 (error-message catalogue); not repeated
here.

9. CONCLUSIONS
================================================================================

9.1 WHAT IS ACTUALLY CONFIRMED (field-observed, [C])
-------------------------------------------------------------------------------
1. A lower-version USB update package is blocked, in both the Y181->Y177 and
   Y181->Y175 directions (§2.2, §5A).
2. Same-version reinstall (Y181->Y181, Y177->Y177) and upgrade (Y177->Y181) are
   allowed (§2.2, §2.3).
3. Both Y177 and Y181 (and Y175) vbmeta images carry rollback_index = 0 — the
   AVB field itself does not encode version ordering (§4.3, §5A).
4. The SOC_HOSTOS (GHS, 85098662) binary is IDENTICAL in Y177 and Y181 (and,
   per §5B, the underlying hardware is identical across Y175/Y177/Y181) — the
   per-release rollback counter, whatever it is, is not baked into a
   per-release GHS binary difference; it must live in persistent state
   (supports, but does not prove, the misc/vda9 hypothesis of §4.2).
5. The OEM RSA-2048 public key was extracted in plaintext from the SOC
   Bootloader's `.oemkeys` ELF section (§8.3); the private signing key was not,
   and is assessed infeasible to extract by software (§8.4).

9.2 WHAT IS INFERRED/HYPOTHESIS, NOT DISASSEMBLED ([inferred])
-------------------------------------------------------------------------------
- The misc-partition (vda9) A/B-metadata structure and the claim that it holds
  GHS's stored rollback counter (§4.2, §4.4). The original document's
  Conclusions (its "11.1 CONFIRMED FINDINGS" items 3 and 5 — "GHS stores
  rollback index in misc partition," "GHS maintains its own rollback counter
  independent of vbmeta") labeled this CONFIRMED while its own Open Questions
  (its "11.2," reproduced below) listed the structure, the comparison method,
  and misc's modifiability as unresolved. That is an internal inconsistency in
  evidence-tagging, not a cross-source contradiction with a settling date; it
  is fixed here by downgrading the claim to [inferred] rather than [C] and is
  carried forward as Open Conflict #3 below, since the original text is not
  being discarded, only re-tagged.
- The exact version-comparison method (string vs numeric, strict `<` vs `<=`).
- Whether the GHS HOSTOS downgrade-compare logic treats Y175/Y177/Y181
  identically (§5A verdict is MEDIUM confidence for this reason).

9.3 OPEN QUESTIONS
-------------------------------------------------------------------------------
1. Exact structure of the A/B metadata in the misc partition.
2. How GHS determines version ordering (string compare? numeric?).
3. Does factory/dealer reset clear the stored rollback index?
4. Can the misc partition be safely modified from Android?
5. Complete list of filename triggers supported by `gm_update_engine` (partial
   list and current corrected account: GBUR §4.1-4.7, not restated here).

9.4 RECOMMENDED NEXT STEPS
-------------------------------------------------------------------------------
1. Dump the misc partition via ADB for structure analysis.
2. Test factory-reset impact on downgrade protection.
3. Disassemble the GHS A/B-metadata/rollback-compare routine directly (string-
   level evidence only, to date).
4. UART console access to capture GHS boot logs during a downgrade attempt, to
   settle Open Conflict #1 (does the "rollback index is too old" message
   actually fire on a Y181->Y177 attempt, or does rejection happen earlier?).
5. Reverse-engineer `gm_update_engine` for the full trigger/version-check list
   (scope boundary with GBUR §4 — coordinate so the finding lands in one doc).

OPEN CONFLICTS
================================================================================

1. Y181->Y177 (and Y175) DOWNGRADE REJECTION POINT — early-reject-at-write/
   update-time vs boot-time AVB/rollback verification after partitions are
   written. (= consolidation-plan Open Conflicts item 8.)
   - Model A ("early reject," §2.2): the 2026-08-17 owner bench re-test found
     that on normal boot a downgrade package produces NO update prompt at all,
     and in recovery mode the progress bar starts then stops with "update not
     supported / invalid" — consistent with a version-gate checked at or near
     update start, before any full partition write-and-boot cycle.
   - Model B (original, Dec-2024, §2.1): a full write to the inactive slot,
     followed by a GHS boot-time AVB/rollback-verification revert and A/B
     fallback. This model is still asserted as CONFIRMED in the document's
     exec summary (now §1), §3.1 ("GHS performs AVB verification... REJECTS
     boot if verification fails... Falls back to original slot on failure"),
     §4.4's flow diagram, §6.1/§8.4-style "verification happens AFTER
     partitions are written" framing, and the original Conclusions item 6
     ("blocked at GHS boot verification") — none of which were revised after
     §2.2 was added.
   - This document's own reader review could not reconcile the two across the
     rewrite; it is carried here unresolved rather than silently picked. Note
     also: an early-reject-at-update-start behavior is at least as consistent
     with an Android-side (`gm_update_engine`/recovery) version check as with
     GHS — which would cut against this document's own headline claim that GHS
     (not Android) is the enforcement point. Owner observation to date does
     not distinguish which component issues the actual rejection.
   - Settling evidence needed: a UART/console capture of a live downgrade
     attempt showing whether the GHS "rollback index is too old" string
     actually fires, and at what point in the sequence.

2. GHS ROLLBACK-CHECK MECHANISM — string-level only, not disassembled. The
   "rollback index is too old" string (§4.1, offset 0x00cf85ac) proves GHS
   *has* a rollback-index comparison; it does not prove the comparison runs
   where either Model A or Model B in #1 above places it, nor does it prove the
   misc/vda9 storage hypothesis in §4.2/§4.4. No disassembly of the compare
   routine exists in this source; kept as hypothesis per §9.2.

3. MISC-PARTITION-COUNTER STATUS: CONFIRMED (original Conclusions) vs OPEN
   (original Open Questions) — the source document's own "11.1 CONFIRMED
   FINDINGS" asserted items 3 and 5 (stored-counter location, GHS's independent
   counter) as confirmed, while its own "11.2 OPEN QUESTIONS" items 1-4 (exact
   structure, comparison method, factory-reset behavior, modifiability from
   Android) list the same mechanism as unresolved. No later dated correction in
   the source closes this gap. Resolved here by re-tagging the claim
   [inferred] rather than [C] (§9.1 item 4 / §9.2) — flagged so the downgrade
   is visible rather than silently applied.
