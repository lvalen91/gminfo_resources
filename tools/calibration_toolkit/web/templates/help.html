Elevated-caution CalDef domains — chime/alert/safety-volume/driver-workload

Correction (2026-11-22): this section previously claimed these groups were "never shipped." That was false — direct verification found 162 real entries from these groups in stock slot 04 alone (seat-belt-reminder and forward-collision chime records, `ADASIS_SUPPORT`, `SAFETY_VOL_OVRD_LEVEL`) and 5 more in slot 05. The gate on them stays; the reason is what they govern, not whether GM has shipped them:

  • GIS604_SafetyRelatedVolumeGroupOverrides — safety-chime volume behavior
  • GIS631_ConfigChimeProd_* (4 variants) — chime/alert sound configuration
  • GlobalChimeGainCals, MuteUnmuteRampTimes, VolumeGroupRampTimes
  • DrivingRestrictions, GIS509_DriverWorkloadRestrictions
  • SFS22_SecurityEventLoggingFRD
  • ADASIS

Treat these as elevated-caution, not as the next experiment — see the customization guide for why.

Loading a whole set

The editor accepts a .zip of several files — e.g. a whole spsCacheInternal/ directory — and sorts out what's in it automatically: signed containers, already-unwrapped containers, and bare .calovride files are all detected per-file; anything else (DLLs, .cfx, logs, manifests) is skipped and listed, not treated as an error. Each recognized module appears as a row with its slot number and a one-line summary of that slot's general purpose; click a row to expand its full entry list. Boolean values get a true/false toggle; Enumeration values get a dropdown of every known labeled value (e.g. for GMBrand: 0=None, 3=Chevrolet, 4=GMC, …) plus a "Custom value" option for anything not in that list. Every entry has an "i" button showing its CalDef description.

The override type schema (verified, 28/28 byte-exact against real containers)

Ten types: Boolean, Integer, Float, Enumeration, String, IntegerArray, FloatArray, EnumIntegerMap, EnumFloatMap, Record, plus BinaryFile for embedded blobs. CRLF line endings, 2-space indent per nesting depth, no trailing newline, self-closing root if empty. This toolkit's editor only exposes the scalar/String types for in-place editing; array/map/record/binary types need the CLI or direct JSON editing (see the entry's raw value column).

What this tool does not do

It does not sign anything, and it does not talk to any radio. A repacked container's digest is recomputed correctly; its RSA signature is carried forward unchanged from whatever template you gave it, and will be stale relative to any edit — exactly as documented for every real bench trial. Getting an edited container accepted by real hardware requires the separate CAN613/614 VIP-RAM bypass procedure in DPS_TYPE4_CUSTOM_CALIBRATION_WORKFLOW.md, which is a live-hardware action, not something this tool automates.
